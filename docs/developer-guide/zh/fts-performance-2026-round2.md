# 全文索引第二轮优化

第一轮提交 `a5e1782d46210d085385e715c985a46bb64367f0` 的正式反馈为 **6.81/50**。评测只返回总分，没有各项耗时。本轮以该提交为直接对照，继续在内核中减少构建、分词和查询的重复工作；基准数据、SQL、计时脚本、评分脚本及固定 baseline 均保持原样。

## 瓶颈依据

在上一版的专用实例上，对原中文查询和 LIMIT 查询另作 CPU 采样，共约 7,000 个用户态样本，无丢样。通用简单合并器的 push/pop/top 合计约 3.7%，结果投影约 1.2%，逐行 bit-vector set 约 1.5%，通用 binary Datum 比较约 1.7%。这些比例是整个采样期间的比例，不是可直接相加的预期加速比。链接器可能合并机器码相同的 `at()` 函数，不能将符号名中的容器类型直接视为实际热点来源。

源码检查还发现：每次 TOKENIZE 调用都创建和销毁词频表；其 hash 桶和节点池都使用锁，而这些表实际只属于一个分词调用；IK 在已解码分类之前又用 `first_valid_char` 校验和扫描同一个 UTF-8 字符。

另对 TOKENIZE 调用采样，8,148 个用户态样本，无丢样。以全系统用户态采样为分母（包含 Python 客户端），`parse_param` 调用链约 5.6%，`ObFTParseHelper::init` 约 1.8%，字典加载器查找中的 `TCRWLock::wrlock` 自身约 1.35%。配置校验、格式化与实际分词分开进行，为复用验证后的配置提供了边界。

## 修改与边界

1. 文档和查询分词的词频表使用无锁桶及无锁节点池。所有使用点均为函数内的局部对象，或该调用链中的引用；共享的停用词表和词典仍保留原同步。查询优化器、两条查询执行路径的显式旧类型也统一为 `ObFTWordMap`。
2. TOKENIZE 在调用线程复用空的词频表，只保留原桶容量和一个节点块。每次调用结束清除所有键；不会缓存输入、词项或 JSON 结果。桶请求数变化时重新创建，保持原输出数组的迭代顺序。重入时使用独立局部表，初始化失败时清理已创建的表。
3. IK 对 UTF8MB4 使用原字符集库的 Unicode 解码器，一次取得长度和字符类型；解码失败时回退原校验和分类，以保留原路径对代理码点等特殊字节的接受行为及错误码。其他字符集走原路径，分类谓词顺序不变。
4. 自然语言模式下，最多三个词项的倒排并集直接比较当前 posting，利用位掩码记录相同最小文档 ID 的词项。每轮只前进上一轮消费的词项，按原词项编号顺序累加分数，保留权重、过滤、LIMIT/OFFSET 和错误传播。布尔模式、更多词项及其他稀疏检索迭代器保留通用合并器。
5. 原 `VARCHAR + CS_TYPE_BINARY` 文档 ID 比较快路径也用于 BMW/block-max 的比较器。其他类型不变，MIN/MAX 扩展值继续由原逻辑处理。
6. 稠密结果批次完成写值后，整批设置 evaluated 标志，仅设置一次表达式状态；不改变各行 Datum 的写入、批次边界和分数。
7. whitespace 分隔符检测一次读取字符分类表，使用原空白、控制符和标点掩码；字符边界处理保持原样。
8. 已存在的字典加载器在读锁下查找并获取 handle 引用；未命中时释放读锁，获取写锁后再次查找，再执行原创建路径，防止并发重复创建。共享词典及停用词数据本身的同步不变。
9. TOKENIZE 复用最近一次验证并格式化的 parser 配置。键包含带版本的 parser 名和原配置的完整字节；线程本地固定缓冲区限制输入配置至 1 KiB、格式化配置至 2 KiB，较大配置回退原路径。仅成功结果进入配置缓存，每次命中仍将配置复制到当前调用的 allocator；不保存输入文本、词项或 JSON 输出。

## 正确性验证方法

新增 `fts_batch_merge_regression.test`，预期结果由上一版生成，覆盖 1,025 行数据、NULL/空文本、1/2/3 词及更多词回退、重复词、全文 ID/分数校验、跨批次分页、相关性排序和过滤、布尔模式、相关子查询、事务更新删除回滚，以及交替 parser、不同长度、长重复文本和错误后的 TOKENIZE 调用。另包含 UTF-8 边界及非法字节经过 SQL 转换后的既有行为。

完整差分使用同一份索引切换二进制，比较 1,668 组 Unicode/混合文本、五种 parser、两种输出模式、字符集转换、全部命中文档 ID、相关性分数及分页结果。另比较 90 组 UTF-8 边界/非法输入，并用 8 个连接各执行 200 次交替调用检查词频表复用，包含 1,200 个不同词项的长文本、NULL、空输入及错误恢复。性能测试与编译、perf 和并发正确性检查分开运行。

## 性能测量方法

硬件、Clang 17 Release `-O2`、WSL2 配置、数据目录和启动参数与第一轮相同。上一版与新版各运行三次原始完整基准，每次都使用新报告文件；参数保持 `ROWS=20000 BATCH=500 ROUNDS=3000 QUERY_ROUNDS=200 SAMPLES=3 WARMUP=30 SKIP_LOAD=0`。类别内先平均单项耗时下降率，再对构建、分词、查询三类等权平均，保留退化项。

本地相对结果用于判断修改收益，不能换算或承诺正式成绩。Linux 编译目录是源码副本，报告中的版本显示为 `unknown`，需以同步核验和保留的二进制区分版本。

补充 CPU 诊断在同一份索引上交错运行两版各两次，使用不同于计分基准的循环数及分词文本，不参与计分。最终版中文、英文、混合、LIMIT 查询的服务器 CPU 均值分别从 `2.420 / 2.900 / 2.425 / 3.300 ms` 降至 `1.995 / 2.595 / 1.985 / 2.945 ms`。但 IK 与 BENG 分词 CPU 均值为 `0.1475 → 0.1485 ms`、`0.1250 → 0.1420 ms`，未证实分词 CPU 收益；不能把全量基准中 43.17% 的分词耗时下降解释为同等 CPU 工作量下降。原始诊断数据保留在 [diagnostics](../benchmarks/fts-2026-round2/diagnostics/)。
